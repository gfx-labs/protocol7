# Agent notes

- Read docs/plan.md first, in particular "Repository layout".
- **Settings go in config, not flags.** A command's settings come from a YAML file read by `--config` (`pkg/support/config`): each key is a flag's long name and a repeatable flag takes a list. A deployment mounts that file from a ConfigMap and keeps container args to the command and `--config`. A new setting is a field with a flag name in the command's kong struct, which makes it settable from the file. Secrets stay in files or PDP, never in the settings.
- This repository is the SDK that each app builds its own worker from. Workflows, activities, tools and support code that more than one app needs belong here, so that an app (protocol7-selfdev, oku-development, oku-review) upgrades by bumping its protocol7 version and does not run another app's images.
- **The SDK holds no prompt text.** It provides mechanics, such as the learnings log (`pkg/orchestration/learning`: entries, validation, the workflow, the store and the activities that write it), and an app writes the curation and the words a model reads on top of it: search, ranking, briefs, tool descriptions, instructions. Do not add model-facing prose to an SDK package; take the text as an argument or leave it to the app. Some prompt text from before this rule is still in the base chat, `pkg/p7` and the MCP transport. It is not a model for new code.
- Packages are grouped under `pkg/` by area (`domain`, `execution`, `orchestration`, `p7`, `support`, `transport`). Put a new package in the group it belongs to.
- **Build model prompts with `pkg/support/prompt`, not `strings.Builder` or `fmt.Fprintf`.** Static prose goes in an embedded `.md` file added with `Template`, so backticks and long text stay readable. An app with many prompt parts loads them as one group with `prompt.Load(embedFS, ...)` (later file systems override earlier ones) and adds them by name with `lib.New(vars).Part("name")`. A directory is a slot with variants (`voice/direct.md`, `voice/default.md`), chosen per use with `lib.Pick("voice", "direct")`, so different outputs can use different personalities from the same library. A part includes another with `{{part "voice"}}` (same Pick, layers and vars; a cycle is an error), so a prompt's structure lives in the markdown and not in Go. Dynamic parts use `Title`, `Heading`, `P` (an indented raw string, dedented, executed as a `text/template` with `{{.name}}` placeholders from `New(prompt.Vars{...})`, and `{{if}}` or `{{range}}` where needed), `Bullets`, `List`, `Codes` and `When` for optional sections. Text from users, issues, diffs, logs or tool output goes in `Fence`, never in `P` or `Template`, so it cannot close the block or run as a template. Check `Err()` after building so a missing key or bad template fails instead of reaching the model. `strings.Builder` stays fine for text that is not a prompt.
- **A workflow change that alters its commands needs a `workflow.GetVersion` guard and a replay test of a history recorded before it.** `testsuite.TestWorkflowEnvironment` cannot export a history, so record it on a dev server: in a scratch test call `testsuite.StartDevServer` (it downloads the CLI through the egress proxy) with `ExtraArgs: "--search-attribute", "Name=Keyword"` for every attribute the workflow upserts (without them an update fails with `BadSearchAttributes`), run a worker, start the workflow, send the signals and updates, then write `client.GetWorkflowHistory` as protojson. Record the old history from a `git worktree` of master, put both in `testdata` and replay them with `ReplayWorkflowHistoryFromJSONFile` (see `pkg/orchestration/learning/replay_test.go`). Removing the guard must fail the old one.

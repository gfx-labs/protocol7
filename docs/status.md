## Temporal SPIFFE server

`temporal/` is a separate Go module. Temporal server 1.32.2 uses API 1.63.5 and SDK 1.44.0. The root module uses newer API interfaces that the server's generated clients do not implement. Keeping those dependency graphs separate lets the server stay on 1.32.2 without downgrading protocol7 clients.

- `temporal/pkg/temporalauth` accepts a `Config` with `TrustDomain`, exact `Identities` and path `Prefixes`. Each `Grant` contains `SystemAdmin`, a map of Temporal namespace names to `reader`, `writer`, `worker` or `admin` role names, and optional `NamespaceAPIs` (`namespace_apis` in JSON). API grants name namespace-scoped WorkflowService method names such as `UpdateWorkflowExecution`, without the service prefix. Unknown methods, cluster-scoped methods and wildcard namespaces are rejected. Exact identities override prefixes. The longest matching slash-terminated prefix wins. Grants are not combined. Prefixes cannot grant system admin.
- A `Grant` may also have `TaskQueues` (`task_queues`): the queues the identity may poll and describe, in every namespace it is granted. It limits the queues that the other grants' calls may name, and grants no call. `{id}` in a prefix grant is the rest of the caller's SPIFFE ID after the prefix, which must be one path element, so `.../ns/x/session/` with `p7-session-{id}` lets `.../ns/x/session/abc` poll `p7-session-abc` and no other queue. A sticky queue counts as its normal queue. The calls it judges are `PollWorkflowTaskQueue`, `PollActivityTaskQueue`, `PollNexusTaskQueue`, `DescribeTaskQueue`, `ListTaskQueuePartitions` and the worker build ID and versioning calls. Respond and heartbeat calls name no queue and are held by the task token, which only a poll hands out, so a session pod that cannot poll another session's queue cannot answer its tasks. Grant such an identity the explicit calls it needs and not the `worker` role, whose list holds the `...ById` responses that need no poll. `TestTaskQueueGrants` runs it over real mTLS. It is not run in a Temporal server.
- `NexusEndpoints` (`nexus_endpoints`) maps each source Temporal namespace to exact endpoint names. The authorizer checks every `ScheduleNexusOperation` command before accepting a workflow-task completion, and checks `StartNexusOperationExecution` for standalone callers. A grant adds no workflow RPC permission. Namespace writer or admin roles alone do not grant Nexus calls. Wildcard sources and endpoints are refused. Direct Nexus HTTP dispatch and callbacks require a system administrator identity because worker-target dispatch runs inside Temporal under its server identity. Tenants use workflow commands rather than the HTTP route. The worker role includes Nexus polling and responses, with the same task-queue restrictions as other polls. `TestNexusEndpointGrants` crosses real mTLS and checks source, identity and endpoint isolation, API permissions and the direct-dispatch bypass. Live verification is pending.
- The claim mapper requires a TLS verified client certificate chain and a single SPIFFE URI SAN in the configured trust domain. A bearer token, an unverified certificate, a missing identity and an unmapped identity grant nothing.
- The authorizer delegates ordinary permissions to Temporal's default authorizer. Temporal 1.32.2's built-in worker bit does not authorize task polling. This package gives it an explicit list of task polling, response, heartbeat and required worker metadata RPCs. The worker bit alone does not grant direct workflow starts, signals, termination, reset, updates, schedules or namespace administration. Explicit namespace API grants add only their named RPCs. The authorizer also checks child-start, external-signal and external-cancel commands in task completions against the target namespace's role or explicit API grant, including commands targeting the caller's own namespace.
- The TLS provider reads a live `go-spiffe` X.509 source on each handshake. It rotates certificates and bundles without files or a helper sidecar. Frontend listeners require verified client certificates. Internode listeners, including an enabled internal frontend, accept only the configured server SPIFFE identity. Server-side verification keeps `VerifiedChains` available to the mapper. Outgoing service and system-worker connections authorize that exact server identity, not a DNS name.
- `temporal/cmd/p7-temporal` starts the server with `temporal.WithClaimMapper`, `WithAuthorizer` and `WithTLSConfigFactory`. It reads Temporal's standard configuration file or embedded environment template, `TEMPORAL_AUTH_MAPPING_FILE`, `TEMPORAL_SPIFFE_ID`, `TEMPORAL_SERVICES` and the standard `SPIFFE_ENDPOINT_SOCKET`. Changes to mapping files require a process restart.
- `p7-temporal proxy` is a loopback-only TCP forwarder for stock Temporal UI and admin tools. Its own workload identity authenticates to `TEMPORAL_FRONTEND_ADDRESS` and authorizes `TEMPORAL_FRONTEND_SPIFFE_ID`. The UI and CLI use plaintext only within their pod. The proxy keeps its SVID and trust bundle current in process. Client TLS configuration explicitly negotiates HTTP/2 with ALPN, including raw proxy connections that do not pass through gRPC's TLS constructor. `p7-temporal bootstrap --namespace <name>` idempotently creates configured namespaces through the same mTLS path. Repeated `--search-attribute Name=Type` flags register missing search attributes in each namespace under the bootstrap admin identity. Types use Temporal's enum names, for example `SelfdevKind=Keyword`. Existing type mismatches fail instead of changing data definitions. Application writer identities need not receive namespace admin for schema registration.
- `containers/temporal/Dockerfile` retains the upstream server 1.32.2 runtime and schema assets, replacing only its server binary. The image workflow publishes `ghcr.io/gfx-labs/protocol7/p7-temporal:<commit>` separately from the worker image and records its digest in the job summary. No deployment is changed by this repository.

The retained test makes real TLS 1.3 connections with generated CA-signed SVIDs through the production TLS provider, mapper and authorizer. It checks namespace isolation, exact worker overrides, writer and reader access, administrator access, prefix boundaries, unmapped identities, missing and untrusted certificates, wrong server identities and the internal frontend boundary. It also requires actual HTTP/2 ALPN negotiation using the same client config as the raw proxy. This regression failed before the client ALPN fix and passed afterward. It uses no mock of this package. Both modules were built, vetted and tested, including the authorization tests with the race detector. The server image was published by CI and its CLI smoke-tested on agent-server. Live SPIRE delivery, a running Temporal cluster and certificate rotation remain separate deployment checks.

A worker identity is not a sandbox. An unsandboxed agent sharing the worker's container can use its identity, poll tasks and forge task responses. A deployment running the host core worker can add `UpdateWorkflowExecution` and `PollWorkflowExecutionUpdate` for owner-decided `p7.ToolCall`, `p7.Permission` and typed-report updates, plus `SignalWithStartWorkflowExecution` if agents run `selfdev review`. This is narrower than writer. Direct starts, direct signals, reset, termination, deletion, schedules and namespace administration remain denied. Owner workflows retain their writer identity for external signals and child starts. The optional `p7 pods` reconciler instead needs a separate worker grant with `StartWorkflowExecution` and `DescribeWorkflowExecution` for probes and owner liveness.

API grants do not filter workflow IDs, types, signal names or update names. An agent with the three host-worker APIs can submit arbitrary updates and signal-with-start requests to any workflow in its namespace. The workflow's tool and permission validators remain responsible for session membership and decisions. A shared worker SVID cannot attest which session issued a call. Cross-namespace access is still denied. Reducing that residual risk needs per-session attestation and request-level policy, or a trusted broker, not a writer role.

## Temporal SPIFFE clients

Every Temporal client that protocol7 makes can connect with mutual TLS. `p7.NewTemporalClient` is the one constructor, used by `p7.NewWorker` and by `p7fx.TemporalClient`. `p7.TemporalSPIFFE` holds `Socket`, the Workload API address, and `ServerID`, the SPIFFE ID the frontend must present. `p7.WorkerConfig.TemporalSPIFFE` and `p7fx.TemporalConfig.SPIFFE` carry it. With `ServerID` empty the client connects in plaintext, as before. A socket with no server ID is refused.

- With `ServerID` set, the client opens a `go-spiffe` X.509 source and waits up to a minute for its first SVID. It presents the SVID and accepts only a server certificate from the bundle that names `ServerID`, over TLS 1.3. The source keeps the SVID and bundle current. Closing the client closes the source.
- `p7 worker`, `p7-worker`, `p7 session` and `p7 pods` take `--temporal-spiffe-socket` (`TEMPORAL_SPIFFE_SOCKET`) and `--temporal-server-spiffe-id` (`TEMPORAL_SERVER_SPIFFE_ID`). An empty socket uses `SPIFFE_ENDPOINT_SOCKET`. The server ID is the value of `TEMPORAL_FRONTEND_SPIFFE_ID` in `p7-temporal`. `p7 dev` starts its own plaintext development server and has no such flags.
- `github.com/spiffe/go-spiffe/v2` 2.7.0, the version `temporal/` uses, adds 1.3 MB to `p7-worker` (44.4 MB to 45.7 MB) and 0.9 MB to `p7` (57.8 MB to 58.7 MB).

Run on 2026-11-15: `go vet ./...`, gofmt, and `go test -race` of `pkg/p7`, `pkg/p7/p7fx` and `pkg/transport/...` with the Temporal CLI on `PATH`. `pkg/p7/temporal_test.go` makes real TLS 1.3 connections with SVIDs signed by a CA it generates. The client's SVID comes from a Workload API served on a unix socket with the `go-spiffe` protobuf service. The server is a gRPC server with `go-spiffe`'s mutual TLS server config, serving the health check and `GetSystemInfo` that `CheckHealth` calls. The test checks that the server sees the client's SPIFFE ID over TLS 1.3, that a server presenting another SPIFFE ID is refused before any call reaches it, and that closing the client ends its Workload API stream. Not run: a connection to `p7-temporal`, SPIRE, certificate rotation and a deployment.

## Egress through PDP, in process

`pkg/transport/egress` lets a Go process make its own HTTP requests through PDP with its SPIFFE identity, with no `pdp forward` container in its pod. `pdp forward` reads no HTTP: it opens an mTLS connection to PDP for each connection it accepts and copies bytes. `egress.Egress` does the same inside an `http.Transport`, by dialing PDP where the transport would dial its proxy, so the proxy conversation (CONNECT for https, an absolute URL for plain http) reaches PDP as the client wrote it.

- `egress.New(ctx, egress.Config{WorkloadAPI, Gateway, GatewayID, CAFile})` opens the Workload API source and waits for the first SVID. `NewFromSource` takes an SVID and bundle the caller already has. `Transport()` and `Client(timeout)` make clients, and `DialGateway` is the raw mTLS dial. `Close` closes the source.
- The gateway must present exactly `GatewayID`, over TLS 1.3, or nothing is sent. `CAFile` is added to the system roots, for PDP's interception CA. The transport takes no proxy setting from the environment.
- Every request made with the client is made as the workload, so PDP's policy judges the process and not the code inside it. Use it in a process whose own code is trusted with that identity, such as a web server. It is not for an agent's pod: there code that is not the process's own shares the identity anyway (see "A worker identity is not a sandbox" above), and the forwarder container makes no difference to that.

Run on 2026-11-16: `go vet ./...` and `go test -race ./pkg/transport/egress`. The test stands in for PDP with a gateway that requires a client SVID, answers CONNECT and terminates TLS with its own interception CA. It checks https and plain http, the identity the gateway sees, an untrusted interception CA, a gateway with another SPIFFE ID or one that offers only TLS 1.2 (no request reaches either), and that `NO_PROXY` and `HTTPS_PROXY` in the environment change nothing. Each of the proxy and TLS 1.3 checks was seen to fail when its line was changed (`ProxyFromEnvironment`, no `MinVersion`). Not run: against a real PDP or a real Workload API (`New` itself, past its argument checks).

## How a process is put together

The commands of both repositories are composed with `go.uber.org/fx` (decided 2026-11-13, user). A long-lived component has a constructor that connects to nothing, and separate start and stop methods: `stream.New` then `Connect`, `stream.NewEmbedded` then `Start`, `coreworker.New` then `Start` and `Stop`, `p7.NewClient` then `Connect`, `p7.NewWorker` then `Start` and `Stop`. A command supplies its flags as configuration values and names its modules. fx starts the components in dependency order and stops them in reverse.

fx resolves the components when the process starts, so a missing one is not a compile error. `wire_test.go` in each repository's `pkg/cli` checks every command's graph with `fx.ValidateApp`.

## How a turn survives

- The turn ID travels in the `_meta` of `session/prompt`, which the journal keeps. A repeated `p7.RunTurn` with the same ID reads the journal first. It returns the recorded result, or attaches to the running turn, and never prompts twice.
- A worker that shuts down leaves the turn running in the shim. A cancel request or the activity timeout sends `session/cancel` and still returns the turn's result.
- A shim that stopped during a turn makes that turn end as `interrupted`. The next turn starts a new shim, which loads the conversation.

## Tools

A workflow offers tools to a session's agent with `SessionSpec.Tools` and answers their calls with `p7.HandleTools`. Each `p7.Tool` has a name, a description, a JSON Schema for its arguments and a `Run` function that runs in the workflow.

- The core worker offers the tools to the harness as one MCP server of type `acp` in `session/new` and `session/load`. The agent sends MCP requests as `mcp/message` on the same ACP connection, so there is no second process or endpoint. towa supports this from 0.4.0.
- `tools/list` is answered from the session's request. `tools/call` becomes the Temporal update `p7.ToolCall` to the workflow that opened the session, sent with no run ID so that it reaches the current run after Continue-As-New.
- The update ID is the session, the shim's process ID and the MCP request ID. A call that the shim sends again to a later connection gets the first call's result and does not run twice.
- The update's validator refuses a session the workflow did not open and a tool it did not offer, before the call enters history. A `Run` error is returned to the agent as a result with `isError`, which is how MCP reports a tool that failed.
- What a call may do is decided in the consumer's workflow. It runs activities for any work outside the workflow.

## Permission requests

A workflow decides the permission requests of its session's agent with `SessionSpec.Permissions`, a function that gets a `p7.PermissionRequest` (session, tool call ID, title, kind, raw input, the agent's options) and returns `p7.Allow()` or `p7.Deny(reason)`. With no function, every request is allowed, as before.

- The workflow calls `p7.HandlePermissions` with the same function at the start of every run, like `HandleTools`. A request becomes the Temporal update `p7.Permission` to the workflow that opened the session, sent with no run ID. The validator refuses a session the workflow did not open.
- The function runs in the workflow, so it may run activities or wait for a signal to ask a person. The agent waits for the answer.
- The shim answers the agent with its own option of the wanted kind: `allow_once` then `allow_always`, or `reject_once` then `reject_always`. When the agent offers none of that kind, the answer is `cancelled`. ACP carries no reason, so the agent is not told one.
- Fail closed: an error from the function, a refused update, and a core worker that cannot reach the owner all deny the request, also on a manager with no tool caller and for a session with no owner.
- ACP's request ID is not visible to the shim's handler, so the update ID is the session, the shim's process ID and a digest of the request. The same request sent again to a later connection gets the first decision. An agent that repeats an identical request in the same shim run gets the same decision.
- A session with `Permissions` and no tools offers no MCP server, and runs on a harness that does not take MCP over ACP.

## Typed reports

`p7.PromptTyped[T](ctx, session, prompt)` runs a turn and returns a `T` that the agent reported by calling the tool `p7_report`.

- A workflow makes its context with `p7.WithReports(ctx)` before `HandleTools` and `OpenSession`, and uses that context for all three and for `PromptTyped`. `OpenSession` then offers `p7_report` as one more tool of the session and `HandleTools` answers it. `Session.Reports` records that, so a session survives Continue-As-New.
- A session's tools are fixed when it opens, so the tool's own schema is only `{"type":"object"}`. Each typed turn carries the JSON Schema of `T` in its prompt context, made with `github.com/google/jsonschema-go` from `T`'s fields and `json` tags. A `T` that is not an object is reported as `{"value": <T>}`. The tool is accepted only while a typed prompt runs on that session.
- A call that does not match the schema is returned to the agent as a tool error, so it may fix the call in the same turn. The last valid call is the report.
- A turn that ended normally with no valid report gets one repair turn, with the same session and the turn ID `<id>-repair`. It says what was wrong and repeats the schema. After that the call fails with `*p7.ReportError`, with `Kind` `missing` or `invalid`. A turn that failed, was cancelled or was interrupted is not repaired and fails with `turn_ended`.
- The report is the tool call. Text in the agent's message is never parsed.
- It was run with a scripted agent, the real shim, the core worker and a Temporal development server (`pkg/p7/report_test.go`). It was not run with a real harness, so whether a model calls the tool reliably from the prompt is not known.

## Closed sessions on disk

`Manager.Close` stops the shim, marks the session closed (`closed_at` in `session.json`) and deletes its snapshot, and leaves the directory, the workspace and the journal, for a while: a person may come back to a chat, and the journal is how the page shows what happened. The workspace is a clone of each repository and what builds left in it, 2.5 to 3 GB for a session in practice, and nothing removed it, so a worker's volume filled (oku-review's 50 GB, with 35 closed sessions).

- Retention: `session.Config.Retention`, the flag `--session-retention` (`P7_SESSION_RETENTION`) of `p7 worker` and `p7-worker`, default 24h, negative keeps for ever. After it, everything in the session's directory is removed except `session.json`, which stays as a tombstone (`purged`, the ID and the close): the session is still closed, `State` says so, and its ID is not opened again.
- When: `Close` removes what is due (a repeated close after the retention does), and `Manager.Retain`, which the core worker runs from `Start` to `Stop` every 10 minutes, calls `Sweep` for the sessions no `Close` visits again. A record from before `closed_at` is aged by its file's modification time, which was its close. A session that is open is never removed, nor a directory with no record, nor one whose record cannot be read. Directories that are not writable (a Go module cache) are made writable to remove them.
- Tests: `pkg/execution/session/retention_test.go` (open never, closed after the retention, tombstone, a close after the retention, off and the default, a record without `closed_at`, the timer).
- Not done: the tombstones themselves stay (a few hundred bytes each), and a machine that never runs the new build keeps its old closed directories until it does.

## Session snapshots

A session's directory can be kept in S3-compatible object storage, so that a session whose machine or pod is lost goes on somewhere else. It is in p7, for the host and the kubernetes backend alike. With no `--snapshot-bucket` there are no snapshots and nothing changes.

- Configuration: `p7.SnapshotStore` (`snapshot.Config`) with `Endpoint`, `Region`, `Bucket`, `Prefix`, `PathStyle` and `Exclude`. It is `coreworker.Config.Snapshots`, and the flags `--snapshot-endpoint`, `--snapshot-region`, `--snapshot-bucket`, `--snapshot-prefix`, `--snapshot-path-style` and `--snapshot-exclude` (each also `P7_SNAPSHOT_*`) of `p7 worker`, `p7 session`, `p7 pods` and `p7-worker`. `p7 pods` takes the same flags, for deleting snapshots. `p7 dev` has none. Credentials are not configuration: the standard AWS environment, shared credentials file (with `AWS_PROFILE`, SSO and credential processes) and web identity, and on Amazon's own endpoint the instance or container role, read again every five minutes so that a rewritten credential file is followed. With none found the client sends anonymous requests.
- What is kept: the whole session directory, `<state dir>/sessions/<id>`: the workspace (`work/`), the shim directory with the journal, and `session.json`. Left out: the shim's socket, pid file, lock and exit record, whatever matches `Exclude` (default `node_modules` and `go-build`; a name with no slash matches at any depth, a path is from the session directory, `path.Match` syntax), and anything that is not a regular file, a directory or a symbolic link that stays inside the tree. An excluded directory is skipped with its content.
- The harness's conversation: with snapshots on, the manager gives the harness `--store.root=<session dir>/harness` (`--harness-store-flag`, empty to pass none), so that towa's conversation is in the snapshot. A harness with no such flag keeps its conversation elsewhere. Its snapshot then restores files and journal, `session/load` is refused, and the next turn starts a new conversation seeded with a summary of the journal. A session that started before snapshots were turned on has its conversation in towa's own store and falls back the same way.
- Key and format: `<prefix>/<session id>/workspace.tar.zst`. Go's `archive/tar` in PAX format (modes, symbolic links, nanosecond modification times; no owners), compressed with `klauspost/compress/zstd` at its default level. It is streamed through a pipe into a multipart upload with 16 MiB parts, with no temporary file.
- When it is written: after `OpenSession` and after each turn that returns, and by `coreworker.Worker.Stop` (SIGTERM) for every session on the machine that is not closed. The tree is walked first and fingerprinted (names, modes, sizes, file modification times, link targets). Nothing is uploaded if the fingerprint is the one in the user metadata of the existing object (or the last one this process wrote). The upload goes to `workspace.tar.zst.tmp`, which is copied over the real key and removed, so a crash or failure mid-upload keeps the previous snapshot. An object over 5 GiB is copied with `ComposeObject`. The snapshot after a turn runs inside the `p7.RunTurn` activity, which heartbeats every two seconds while it is written, so a snapshot that takes longer than the activity's 10 second heartbeat timeout does not fail the attempt. A snapshot that fails is logged and does not fail the turn. The next one tries again. A file that changes while it is being written is cut or zero-padded at the size the walk saw, and the next walk sees the change.
- When it is read: `coreworker.Config.Session`, which `p7 session` sets from `--session`, makes `Start` restore that session before the worker polls, and fail if it cannot. Any manager also restores a session when `Open` or `RunTurn` finds no `session.json` for it and a snapshot exists, which covers the host worker on a machine whose disk was lost. The `RunTurn` activity heartbeats every two seconds during that restore, as it does during the snapshot after a turn, so a restore longer than its 10 second heartbeat timeout does not fail the attempt. `Open` and `CloseSession` have no heartbeat timeout, and the session worker's restore at start happens before it polls. A session whose directory is on the machine is not restored. The archive is extracted into `.restore-*` beside the session directory, and the stream is read to its end with the zstd checksum before the directory is renamed into place, so a cut or damaged snapshot leaves what was there. Entries with `..`, absolute names, a symbolic link that may leave the tree (absolute, climbing above the root, or with `..` after another element), an entry below a link, and any type but file, directory and symbolic link are refused with `snapshot.ErrUnsafeArchive`. The `shim_pid` of the record is cleared, so the next turn starts a shim and the harness loads the conversation. The journal continues from its last sequence number.
- Deleting: `Manager.Close` marks the session closed and then deletes the snapshot, and a closed session is not snapshotted. Writing and deleting a session's snapshot share one lock in the manager, so a snapshot that is being written when `Close` runs is deleted once its write is done, and one that starts after the mark sees it. `p7 pods`, with the snapshot flags, deletes the snapshot of a pod that reconciliation deletes because its owner is gone or its session is closed (not one that was only slow to become ready), and of a pod that `p7.DeleteSessionPod` deletes. In both it waits until the API says the pod is gone and then deletes the snapshot, so that a pod's worker stopping cannot write it again. That activity heartbeats while it waits, and the workflow gives it 20 minutes and a 30 second heartbeat timeout (`podDeleteOptions`), more than the 12 minutes that the worker may take to write its last snapshot. The poll of 1 second is not configurable. A pod that is still there after 20 minutes fails the attempt, and the retry waits again, up to ten attempts.
- Library: `github.com/minio/minio-go/v7`. It adds about 4 MB to `p7-worker` (40.1 MB to 44.3 MB). A probe program with the S3 service, config and upload manager of `aws-sdk-go-v2` linked to 16.4 MB, against 1.9 MB for an empty program, which was not tried in p7-worker itself. `johannesboyne/gofakes3` is a test dependency, in `pkg/execution/snapshot/snapshottest`.
- Needs in the deployment, not done here: the bucket; credentials; the flags in the session pod template and for `p7 pods`; a `terminationGracePeriodSeconds` that covers the snapshot at stop (the command's stop timeout is 12 minutes when snapshots are on); and a lifecycle rule for incomplete multipart uploads. A session pod that is lost is made again by the workflow that runs its turns (see "A lost session pod").
- Work since the last snapshot, at most the turn in progress, is lost on a hard node failure. The workflow's retry runs the turn again.

## A lost session pod

A pod that a node drain, an eviction or a person deleted leaves nobody on the session's queue `p7-session-<id>`. A turn on the kubernetes backend (`p7.PromptText`, `PromptTextFuture`) therefore lets each attempt of its `p7.RunTurn` activity wait one minute to be taken (`podLostAfter`). An attempt that is not taken fails with a schedule-to-start timeout, which the activity's retry policy does not retry, and the workflow requests the pod again with `p7.StartSessionPod` for the same session and owner, then runs the turn again with the same turn ID. The request creates the pod if it is gone, and finds it (409) if it exists, is starting or is still ending, so the loop is safe whatever the cause of the wait. A turn cut off mid-turn takes the same path: its heartbeat times out after 10 seconds and the retry waits on the empty queue. It gives up after 40 such waits (about 40 minutes, which covers a pod ending slowly while its worker writes a last snapshot, and the new pod's image pull and restore) and returns the timeout. A cancelled turn leaves the loop at once.

- The new pod is `p7 session` with the same `--session`. With snapshots, its worker restores the session's directory before it polls, so the session continues from the last snapshot: after the last turn that returned, and at the old pod's stop if its worker ran its SIGTERM handling. The turn that was running is run again. Without snapshots the new pod has no such session and the turn fails with `ErrorSessionNotFound`.
- `TestALostPodIsMadeAgain` runs it with a development server and a stand-in that stops the session's worker and starts it again. The pod API, the snapshot restore in a real pod and a mid-turn loss were not run in a cluster.

## Session pods that nothing owns

A session pod outlives a workflow that failed, was terminated or lost its `CloseSession`. `p7 pods` therefore reconciles once when it starts and then every `--reconcile-interval` (five minutes by default, `P7_RECONCILE_INTERVAL`), on the replica that holds the lease (below).

- It lists the pods with the label `p7.gfx-labs.io/managed=true` in its namespace, and deletes a pod, with a UID precondition, for the first of these reasons that holds. It logs each deletion as `session pod deleted by reconciliation` with the `session`, the `pod` and the `reason`.
  1. `its owner workflow is not running`: the pod's owner annotation names a workflow whose latest run is not running, or that Temporal does not know. A workflow that continued as new is still running.
  2. `it is not ready after its open timeout`: the pod has not had its `Ready` condition for longer than the timeout in its `p7.gfx-labs.io/open-timeout` annotation, which is the session's `OpenTimeout` (15 minutes by default; `--open-timeout` for a pod without the annotation). The time counts from the condition's last change, or from the pod's creation if it has none, so a pod that was ready is not deleted for a restart shorter than the timeout.
  3. `its session is closed`: a ready pod is asked, through the workflow `p7.ProbeSessionPod` on the backend's queue, which runs the activity `p7.SessionState` on the session's queue. The pod's worker answers from its session record.
- A check that cannot be made is logged and the pod is left for the next pass: Temporal not answering, a pod that does not answer within 30 seconds, and a pod whose image lacks `p7.SessionState` (a pod keeps the image it was created with). A pod without an owner annotation is not checked for its owner. A pod that is being deleted is skipped.
- `p7 pods` needs the right to list pods, as well as create and delete them. No deployment runs the backend yet, so no role was changed.
- Run against a Temporal dev server and a stand-in for the pod API: owners that run, failed, were terminated or never existed, a closed session, a pod not ready past its timeout and one still starting. Not run in a cluster.
- One reconciler runs across the replicas of `p7 pods`. They campaign for a `coordination.k8s.io` Lease named `--lease-name` (`P7_LEASE_NAME`, default `p7-pods-reconciler`) in the pod namespace, and only the holder runs passes. The holder renews it every `--lease-duration`/7.5. It releases it at a clean stop, and another replica leads within one retry period. A holder that dies or is cut off from the API server stops leading after two thirds of `--lease-duration` (`P7_LEASE_DURATION`, default 15s) without a renewal, and another takes over once the record has not changed for a whole duration. Replicas never compare the clocks in the lease. Each logs `session pod reconciler elected` and `session pod reconciler stopped leading` with its `identity`, which is the pod's host name and a random suffix. The service account of `p7 pods` needs get, create and update on `leases` in its namespace, in addition to pods. A Temporal Schedule was not chosen, because the pass needs the pod API and the worker's SPIFFE grant denies schedules. client-go's `leaderelection` was not used, because it adds 34 MB to the binary (`p7` 58.7 MB to 92.4 MB); `lease.go` is the same protocol on the backend's plain HTTP calls.
- Run: two reconcilers over one fake API server make one pass per interval between them, the other takes over within a retry period of the leader's stop, and takes over after the lease expired when the leader is cut off (`TestTwoReconcilersMakeOnePassPerInterval`). Not run in a cluster, and no deployment runs `p7 pods` yet, so no role grants leases.

## Session pools

`p7.SessionSpec.Pool` (a `p7.SessionPool`, which is `domain.PoolSpec`) puts a session on a worker of a pool on the kubernetes backend, instead of a pod of its own. The workflow that opens the session chooses the spec in Go: `Name`, `MaxWorkers` (1 to 16), `SessionsPerWorker`, `IdleTimeout` (zero is 5 minutes) and `Pod` (an image, resources and environment variables that replace those of the template's session container: `Env` changes the value of a variable the template has, such as a token placeholder, and refuses one it lacks, and `NoSnapshots` starts the worker without the template's `--snapshot-*` flags and `P7_SNAPSHOT_*` variables, which a pool whose identity has no snapshot grant needs because its first restore would be refused). protocol7 reads no meaning into the name, which is 8 to 32 of a-z and 0-9: the caller derives it from everything that decides what a session may do, because the sessions of a pool share its workers' files, processes and queues, and one identity. With no pool nothing changes: one pod per session, and the host backend, as before. Both stay as they are while the pool is new; a pod of one session is a pool of `SessionsPerWorker: 1` in all but its path.

- **One workflow for each pool.** `p7.Pool` (ID `p7.pool/<name>`, on the queue `p7-kubernetes`, run by `p7 pods`) holds the pool's state: workers by slot, sessions by worker, and the sessions that wait. It is the only thing that makes or deletes the pool's pods, in its loop, with activities. `p7.PlaceSession` (an activity of the backend that update-with-starts the workflow, so it starts when it is not running) sends the update `p7.pool.place` and returns the worker's slot, pod and queue when a worker has room. **The update never waits.** A session that has no room is put in the queue and answered "pending" at once, and the activity asks again every 2 seconds (and heartbeats), so a waiting session holds no update open: Temporal allows ten in-flight updates in a workflow, which would otherwise limit the queue to about ten sessions. Any number may wait, in the order they first asked. A caller that stops asking for a minute (its activity was cancelled) is dropped from the queue, as is a failure that nobody read. `p7.ReleaseSession` sends `p7.pool.release`. The workflow ends when it holds nothing, and continues as new when Temporal suggests it.
- **Placement.** A session goes on the fullest worker that has room, so that the others empty. When all are full and the pool has fewer than `MaxWorkers`, it makes a worker in the lowest free slot and places the session there. When the pool is full the session waits, in order, until one is released. A session that is placed and asks again gets its place after the pool has looked at its pods: the first ask is answered "pending" with the number of the last look, and the next, a moment later, carries it.
- **Workers.** The pod `p7-pool-<name>-<slot>` has the label `p7.gfx-labs.io/pool` and `.../worker`, no session label (so a ClusterSPIFFEID gives it the pool's identity), and runs `p7 session --pool <name> --worker <slot>` on the queue `p7-pool-<name>-<slot>` (`P7_POOL`, `P7_WORKER`, `P7_TASK_QUEUE`). The queues are named for the slot so that a deployment can list a pool's queues, up to 16, in its identity's grants and does not need a pattern. Starting a worker waits (heartbeating) for a pod of that slot that is ending.
- **Idle and lost workers.** A worker with no session for `IdleTimeout` is deleted, without waiting for the pod to end. Every 30 seconds while it has workers, and when a placed session asks again, the pool lists its pods: a worker whose pod is gone, ending, failed or not ready for 15 minutes is lost, its sessions lose their place, and the pod, if it is still there, is deleted. A pod of the pool that no worker has, and is two minutes old, is deleted. A session whose owner workflow is not running is closed on its worker, its snapshot deleted, and its place released. `p7 pods` reconciliation deletes the pods of a pool whose workflow is not running.
- **Recovery.** A turn that finds nobody on its worker's queue waits one minute and then places its session again (`SessionSpec.Pool` is kept in the `Session`): the session's `TaskQueue` and `Pod` change to the new worker's, which restores the session from its snapshot the first time it is used, as a worker of one session does.
- **Snapshots.** A pool's sessions keep their snapshot at `<prefix>/pools/<name>/<session>/workspace.tar.zst` (`domain.PoolSnapshotPrefix`): `p7 session --pool` appends it to `--snapshot-prefix`, and the pool deletes under it. The path does not name the worker, so a session that moves finds it. It is not `<prefix>/<session>/`, because the identity of a pool must be limited to one prefix that holds exactly its sessions, and a static policy cannot name a changing set of sessions.
- **Rights.** `p7 pods` needs, besides pods in the namespace, Temporal's `StartWorkflowExecution`, `ExecuteMultiOperation` (update with start), `UpdateWorkflowExecution`, `PollWorkflowExecutionUpdate`, `DescribeWorkflowExecution` and `QueryWorkflow` (the last for operators; the pool's code does not use it).

Run: `pkg/orchestration/kubernetes/pool_test.go` against a Temporal development server with the real activities over a pod API stand-in: a pool of 3 workers with 3 sessions each places 9 sessions on 3 pods and makes the 10th wait until one is released, an empty worker goes after the idle timeout and the pool's workflow ends, the sessions of a deleted worker are placed again on a new worker, pools do not share pods, an owner that is gone has its session closed and released, a session released while its worker starts, fifteen sessions waiting (more than ten updates) and placed in the order they asked, a caller that stops asking leaving the queue, and specs are checked. `TestSessionsOfAPoolAreRecoveredOnAnotherWorker` (`pkg/p7`) runs two sessions in one pool, loses their worker with its disk, and checks that each is placed on another worker and finds its own files and conversation from its own snapshot and not the other's. `p7 session --pool` flags, and the domain names, are tested. Not run: a cluster.

## Session limit

A session that names a limit waits for a place in it, and `Session.Close` gives the place back.

- The state of a limit is one Temporal workflow per name, `p7.limit/<name>`, served by every `p7.Worker`. The first request starts it with a signal. It continues as new after 500 messages or when the server suggests it. No database is involved.
- The messages are signals. A workflow asks with `p7.limit.request`, the limit answers with `p7.limit.granted/<lease>` to the asking workflow, and the holder releases with `p7.limit.release`. A cancelled `OpenSession` releases its place, and so does an open that fails.
- A higher `Priority` goes first, and equals go in the order they asked. `LimitConfig.Aging` adds one point per interval waited, so that a waiter is not starved. It is off by default.
- The capacity of each name is in `WorkerConfig.Limits.Capacity`, as an exact name or a pattern with `*` (`repo:*`). A name with no capacity fails `OpenSession` with `ErrorLimitNotConfigured` and does not wait. The asking worker's configuration is sent with each request, so a changed capacity reaches a limit that is already running. Lowering it revokes nothing.
- A limit workflow looks every `LimitConfig.Reconcile` (a minute by default) for holders and waiters whose workflow is no longer running, and frees them.
- Limit workflows run on `LimitConfig.TaskQueue`, or on the queue of the first worker that asks. Consumers on several queues that share a limit should name one queue and serve it.

Departures from the plan: a session names one limit, not a list, so a session cannot yet take several limits together. The deployment-wide limit of 20 is not set: it is a name and a number in a consumer's configuration. Pending waits are not ticketd rows, and the attention list does not exist, so `p7.QueryLimit` is the only view of a queue. Temporal's task queue priority and fairness were not checked as a substitute.

## Known limits

- Snapshots: a session is snapshotted only when a turn or an open returns, and when the worker stops. A turn that runs for hours is lost with its node. A pod that stays up past the delete's 20 minutes and then writes a snapshot leaves one behind: the delete fails, and its retry deletes it only if the pod is gone by then. With snapshots on, a store that cannot be reached, or credentials that are refused or unreadable, make `Open` and the first turn of a session that has no local record fail with the store's error, and the workflow's retry policy decides how often they are tried again. This is chosen: a manager that cannot tell whether a snapshot exists must not create the session anew, because its first snapshot would replace the one it could not read. Once a session is on the machine, a store that fails only makes the snapshots after its turns fail with a warning, and the turns go on. The 5 GiB multipart copy, a real S3 or SeaweedFS, and the real towa's conversation in `--store.root` were not run.

- A chat's agent runs unsandboxed as the user who runs the worker, with that user's git and ssh credentials. The chat's instructions tell it to push only when asked. Nothing enforces that.
- No chat has pushed a branch or opened a pull request yet. That path is not run.
- The web UI has no authentication. It listens on the loopback address by default.
- The chat list reads at most 200 workflow executions and does not page.
- A closed chat answers its state query only while a selfdev worker runs and Temporal still keeps its history.
- Frames stay in the stream for 30 days and nothing archives them. The journal on the session's machine is the full record.
- A Stop that arrives before the turn's activity started drops that message without sending it.
- A harness that prints a secret to standard error would show it on the chat's page when it stops while starting. Nothing redacts those lines. towa with proxy-held accounts holds only placeholders.
- A turn is retried ten times over about five minutes by default. The selfdev chat sets its own policy, which stops at once on a harness that cannot start. Another consumer has to do the same.
- Stop can take up to about nine seconds to end a turn, because the cancel waits for the activity's next heartbeat.

- Worker Versioning. `p7.WorkerConfig` takes a deployment and build ID, and that code was only compiled.
- A session whose shim exits on its idle limit. Stopping the shim by hand between turns was run, and the next turn loaded the conversation.
- A harness that refuses to load a conversation, which starts a new one seeded with a summary of the journal.
- A turn that reaches its activity timeout.
- An activity retry that finds its turn still running and attaches to it. Both restart cases above ended their turn before the new worker started. The session manager does attach in its test and in the run against towa.
- More than one machine, and any harness other than towa.

## Builder and the webhook bus

`p7 builder` serves the build queue and, with `--hooks-url`, also takes pushes from the webhook bus to warm the cache. The bus is the optional part: `hooks.SubscribeRetrying` logs a failure to reach it (no route, an identity or consumer not granted) and tries again, waiting 5 seconds growing to 5 minutes, and never ends the builder. Before, `Subscribe`'s error ended the builder's errgroup, and a builder whose network policy did not allow the bus crash-looped (24 restarts in 5.5 hours in p7-oku and p7-oku-review) with its build queue down too. Test: `TestSubscribeRetryingSurvivesAnUnreachableBus`. A builder that cannot reach the bus is not told apart from one that is up except by the warnings in its log.
